<overview>
## Problema
Atualmente, para testar se uma `QueryCompose` (intenção) está sendo detectada corretamente e gerando a resposta esperada, o administrador precisa criar um atendimento real ou usar ferramentas externas. Isso gera ruído no banco de dados (atendimentos de teste) e é ineficiente.

## Usuários Alvo
Administradores do sistema e Gerentes de Treinamento da IA.

## Métricas de Sucesso
- Capacidade de simular uma interação completa (input -> detecção -> resposta) sem criar registros de `Attendance`.
- Visualização clara da Intent detectada e da resposta gerada na mesma tela de verificação.
- Feedback imediato para o administrador ajustar a `QueryCompose` se a resposta não for satisfatória.
</overview>

<functional-decomposition>
## Árvore de Capacidades

### Capacidade: Simulação de Atendimento (Playground)
Permite testar configurações de IA em um ambiente isolado e efêmero.

#### Feature: Chat de Simulação Lateral
- **Descrição**: Interface de chat embaçada na tela de verificação de Query Compose para testes rápidos.
- **Entradas**: Mensagem de texto do usuário.
- **Saídas**: Resposta da IA e Metadados de detecção (Tag/Grupo da Intent).
- **Comportamento**: 
    1. Recebe mensagem.
    2. Busca `QueryCompose` similar usando a mesma lógica de produção.
    3. Gera resposta usando LLM com o comportamento encontrado (ou fallback).
    4. Retorna resposta + metadados sem persistir histórico.

</functional-decomposition>

## Cadeia de Dependências

### Camada Fundação (Fase 0)
- **[AI Engine]**: Módulo existente que provê `FeaturesCompose` e acesso ao LLM.

### Camada Core (Fase 1)
- **[Simulation Service]**: Depende de [AI Engine]. Implementa a lógica de `simular_interacao`.

### Camada Aplicação (Fase 2)
- **[Treinamento Views]**: Depende de [Simulation Service]. Expoe a funcionalidade via HTTP/HTMX.

<implementation-roadmap>
## Fases de Desenvolvimento

### Fase 1: Backend de Simulação
**Objetivo**: Criar o serviço capaz de processar uma mensagem e retornar a resposta simulada.

**Tasks**:
- [ ] Implementar SimulationService (depende de: nenhuma)
  - Critério de aceite: Método `simular_interacao` recebe string e retorna dict com resposta e intent.
  - Estratégia de teste: Teste unitário/manual chamando o serviço com inputs conhecidos.

### Fase 2: Interface de Usuário
**Objetivo**: Integrar a simulação na visualização de Query Compose.

**Tasks**:
- [ ] Criar View e URL de Simulação (depende de: SimulationService)
  - Critério de aceite: Endpoint aceita POST e retorna HTML da resposta.
- [ ] Implementar UI de Chat Lateral (depende de: View)
  - Critério de aceite: Painel expansível ou fixo na direita com input e área de mensagens. Integração via HTMX.

**Entrega**: Funcionalidade completa de teste de intents na tela de verificação.
</implementation-roadmap>

<test-strategy>
## Estratégia de Testes

### SimulationService
**Caminho feliz**:
- Input: "Qual o horário de funcionamento?" (Intent cadastrada)
- Esperado: Resposta contendo o horário e Intent "HorarioFuncionamento" detectada.

**Casos de borda**:
- Input: "Texto aleatório sem sentido"
- Esperado: Resposta de fallback ou "Não entendi", Intent vazia ou None.
- Input: Mensagem vazia
- Esperado: Tratamento de erro ou validação prévia.

**Casos de erro**:
- Erro no LLM (timeout/key inválida)
- Esperado: Mensagem de erro amigável para o usuário no chat.
</test-strategy>
